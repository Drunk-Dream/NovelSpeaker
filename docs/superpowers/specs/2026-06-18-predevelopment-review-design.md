# 开发前最终方案审查结论

## 背景

本次审查针对 `docs/` 中的首版方案，目标是在正式开发前完成最后一次实现性收敛，重点关注：

- MVP 承诺是否过宽。
- 模块边界是否会导致返工。
- 里程碑和 backlog 顺序是否利于纵向切片。
- 风险、测试和默认决策是否足够明确。

审查结论采用“平衡收敛”策略：保留长期正确的分层和扩展边界，但缩小首版承诺，优先确保“TXT 导入 -> HTTP TTS -> 连续播放 -> 缓存 -> 恢复进度”主链路稳定落地。

## 关键调整

### 1. MVP 兼容边界收紧

第一版明确承诺：

- GET
- POST JSON
- POST Form
- 自定义 Header 和 Body
- 会话内 Cookie
- 只读 LoginInfo 输入
- `speakText`、`speakSpeed`
- `{{ ... }}` 表达式
- 少量白名单兼容辅助函数

第一版明确不承诺：

- Cookie 持久化
- Windows 本地 TTS 回退
- `jsLib`
- 复杂 `source.get/put` 可变状态语义
- WebView 登录
- 兼容所有社区规则

### 2. 运行时边界切硬

规则系统拆分为三层：

- 导入与持久化模型：保存原始 JSON 和用户配置。
- 规范化运行时模型：仅包含当前版本真正支持的能力。
- 请求执行模型：规则求值后得到的 `ParsedTtsRequest`。

播放链路只依赖规范化模型和请求执行模型，不直接理解导入 JSON 细节。

### 3. 播放编排职责拆分

`PlaybackCoordinator` 只负责：

- 会话生命周期。
- 用户命令入口。
- 状态推进与串行化。
- 协调当前段解析、音频提供、预取调度和进度保存。

以下职责拆到协作者：

- `PlaybackAudioProvider`：缓存命中或在线生成当前段音频。
- `PrefetchScheduler`：预取窗口、请求去重和取消。
- `ProgressService`：保存和恢复位置。
- `IAudioPlayer`：本地音频播放控制。

### 4. 里程碑顺序调整

调整后的核心顺序：

1. M0 工程骨架
2. M1 本地播放纵向切片
3. M2 TXT 导入和章节解析
4. M3 文本分段与进度模型
5. M4 最小 HTTP TTS
6. M5 连续播放状态机
7. M6 当前段缓存
8. M7 常用 HTTP 规则、限流与预取
9. M8 规则管理与产品化 UI
10. M9 质量和发布

原则是先打通稳定播放主链路，再叠加缓存优化和规则管理体验。

### 5. 风险与测试收口

第一版测试重点改为风险驱动，优先覆盖：

- 章节解析和文本分段稳定性。
- 模板求值和 JavaScript 安全隔离。
- 请求解析、错误分类和日志脱敏。
- 缓存键、原子写入和损坏缓存恢复。
- 播放状态机、旧会话隔离和预取竞态。

同时将“真实规则样本集”提升为正式交付物，维护 3～5 个已脱敏代表性规则样本。

## 默认决策

为避免开发期反复讨论，第一版直接采用：

- 暂停时最多继续预取 1 个段落。
- 当前段最终失败后暂停，用户选择重试或跳过。
- 保存段内音频时间。
- 第一版重点支持 MP3 和 WAV。
- 无 Content-Type 时按文件头和解码结果辅助识别。
- 删除书籍默认不删除缓存，由用户显式选择是否清理。
- 单本书专属规则和语速推迟到第二阶段。
- 发布形式先使用自包含便携 ZIP。

## 结果

本次审查后，项目文档应统一表达为：

- 第一版是“兼容 Legado 风格常见 HTTP TTS 规则”的 Windows 小说听书应用。
- 首版不追求最大兼容度，而追求主链路稳定、边界清晰、可逐步扩展。
- 所有后续计划和任务拆分都应围绕这一收紧后的 MVP 定义推进。
