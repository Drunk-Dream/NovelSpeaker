# 串行实现、审查与提交

严格按本 Skill 执行所选代码任务。不得跳过审查，不得在审查通过前提交，不得并行处理多个任务切片。

## 前置检查

开始前：

1. 确认当前目录位于 Git 仓库中。
2. 确认项目已配置名为 `code_reviewer` 的自定义审查 agent。
3. 读取适用的项目说明、`AGENTS.md`、开发规范和任务要求。
4. 记录初始 `git status`，识别任务开始前已经存在的修改。
5. 不得覆盖、清理、暂存或提交与当前任务无关的既有修改。
6. 将任务拆分为边界清晰、可独立实现、验证、审查和提交的任务切片。

如果任务本身足够小且逻辑上不可再拆分，可以只创建一个任务切片。

## 串行约束

- 任何时刻只能处理一个任务切片。
- 当前切片完成实现、验证、审查和提交之前，不得开始下一切片。
- 不得并行创建或运行多个审查线程。
- 每个任务切片必须使用一个新建的、独立的 `code_reviewer` 审查线程。
- 同一任务切片的所有复审必须继续使用最初创建的同一个审查线程。
- 不得使用其他审查线程替代或协助当前切片的审查。

## 每个任务切片的执行流程

### 1. 定义切片

在修改代码前，明确：

- 当前切片的目标；
- 范围和不包含的内容；
- 验收标准；
- 预计涉及的文件或模块；
- 适用的验证方式。

切片范围应足够小，使其 diff 可以独立理解和审查。

### 2. 实现

由当前执行线程完成当前切片的全部代码修改。

要求：

- 遵循现有架构、接口和项目约定；
- 只修改完成当前切片所必需的内容；
- 补充或调整必要的测试代码；
- 不得混入无关重构、格式变化或清理工作；
- 持续检查工作区，避免影响任务开始前已有的修改。

### 3. 验证

当前执行线程负责执行与改动相关的验证，包括适用的：

- build；
- format；
- lint；
- typecheck；
- test；
- 其他项目规定的检查。

只运行与当前切片合理相关的验证，记录执行命令和结果。发现问题时先修复并重新验证。

在进入审查前，必须：

- 实现已满足验收标准；
- 必要验证已完成；
- 检查完整 `git diff`；
- 确认 diff 中没有无关修改；
- 确定供审查使用的 diff 范围和基准。

### 4. 创建审查线程

为当前任务切片新建且只新建一个 `code_reviewer` 审查线程。

不要显式覆盖其模型或推理强度，使其按照项目自定义 agent 和当前 Codex 配置解析模型设置。

向审查线程提供：

- 当前切片的目标和背景；
- 验收标准；
- 明确的改动范围；
- diff 基准以及如何查看完整 diff；
- 任务开始前已存在且应排除的修改；
- 已执行的验证命令及结果；
- 审查所需的关键设计约束和上下文。

明确要求它：

- 审查当前切片的完整代码改动；
- 只进行静态代码审查；
- 不修改文件；
- 不运行 build、format、lint、typecheck、test、benchmark 或服务；
- 按其规定格式返回 `PASS` 或 `CHANGES_REQUESTED`。

等待审查完成后再继续。

### 5. 处理审查意见

#### 返回 `CHANGES_REQUESTED`

逐项处理审查意见：

1. 验证问题是否成立。
2. 修复所有成立的问题。
3. 对不成立的意见，准备具体代码依据和可验证的解释，不得直接忽略。
4. 重新运行受修改影响的必要验证。
5. 再次检查当前切片的完整 diff。
6. 将以下内容交回同一个审查线程：
   - 最新完整 diff 的查看方式；
   - 对上一轮每项意见的处理结果；
   - 新的验证命令及结果；
   - 对未采纳意见的具体依据。
7. 要求同一个审查线程重新检查完整改动，并确认修复没有引入新问题。

重复“修改—验证—完整复审”，直到同一个审查线程明确返回：

`结论：PASS`

不得自行宣布审查通过，也不得仅根据局部修复结果结束审查。

#### 返回 `PASS`

确认该结论审查的是当前切片的最终完整 diff。

如果 `PASS` 之后发生任何可能影响代码行为、接口、配置、数据格式或测试语义的修改，则该结论立即失效。必须完成必要验证，并将最新完整 diff 交回同一个审查线程重新审查，直到再次获得 `PASS`。

### 6. 原子提交

只有在最终完整 diff 获得 `PASS` 后才能提交。

提交前：

1. 再次检查 `git status` 和完整 diff。
2. 确保没有混入任务开始前的修改或其他切片的改动。
3. 按逻辑将当前切片拆分为一个或多个原子提交。

原子提交要求：

- 每个 commit 只有一个明确目的；
- 每个 commit 的改动逻辑完整；
- 不同模块、性质或关注点的修改尽量分开；
- 每个 commit 可独立理解和审查；
- commit message 简洁、准确并描述目的；
- 不得使用一次性提交掩盖多个无关改动。

可使用交互式暂存或按文件、按补丁暂存来组织提交，但不得误暂存既有无关修改。

如果暂存、提交钩子或提交准备过程修改了文件，必须：

1. 停止提交后续内容；
2. 检查修改；
3. 重新运行必要验证；
4. 将最新完整 diff 交回当前切片的同一个审查线程；
5. 再次获得 `PASS` 后再完成提交。

### 7. 完成切片

只有同时满足以下条件，当前切片才算完成：

- 实现满足验收标准；
- 必要验证已通过；
- 同一个 `code_reviewer` 审查线程已对最终完整 diff 返回 `PASS`；
- 所有审查问题均已处理；
- 全部修改已按原子提交原则提交；
- 工作区中不存在属于当前切片的未提交修改。

满足后才能开始下一任务切片。下一切片必须创建新的独立 `code_reviewer` 审查线程，并重新执行完整流程。

## 任务完成

全部任务切片完成后，汇总：

- 已完成的任务切片；
- 每个切片执行的关键验证；
- 每个切片的最终审查结论；
- 创建的 commits 及其目的；
- 仍存在但不属于本任务范围的既有工作区修改或风险。

不得在任何任务切片尚未审查通过或尚未提交时宣告整个任务完成。
